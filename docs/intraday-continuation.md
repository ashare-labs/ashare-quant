# One holding day after a settled intraday account

The frozen v2 plan accepts one date and requires an empty account for its first intent. Reusing that plan on the next date is invalid. This candidate adds an explicit, finite continuation without recreating cash, positions, trades, fees, identifiers, or the native ledger.

The original runtime must complete the first day's close. `continuation_cli build-plan` reads that verified closing checkpoint and derives the successor daily capture from its sealed close input. It writes only a proposed plan file. It does not bind an account, fetch market data, or start a worker. The caller specifies the next actual continuous-session start; the intent deadline is five minutes later and execution deadline fifteen minutes later.

`continuation_cli bind` requires the exact prior state SHA, the exact plan file SHA, and both frozen runtime digests. Binding retains the original account identity, configuration, engine pin, head, and all first-day native files. It saves the original control file byte for byte as `continuation-origin.json`, then atomically adds a continuation manifest to the current control file. Repeating the same bind is idempotent. Binding requires one completed parent day, a verified owner daily packet, the parent's exact closing capture, the owner's unchanged action baseline covering both dates, and a next-open calendar match. Native dependencies and the RQ runtime must remain identical; the approved source runtime is recorded separately. Binding cannot finish an incomplete parent or execute an old date.

This candidate supports only the immediately following day in the same month and only the existing equal-weight holding schedule. The successor target is the actual native closing quantity for each security. The previously cancelled remainder remains cancelled. A rebalance requires a different implementation; this continuation must refuse it. Both control validation and the native submit path prohibit any nonzero order delta.

The next day still needs real owner admission and a fresh complete minute strictly after its intent. The original time, state, owner, action, price, volume, and revision checks remain in force. `intraday_cli prepare`, `deliver`, and `advance` use the same online root and original native parent checkpoint. Native BEFORE_TRADING releases the prior day's T+1 restriction. It is normal for sellable quantities to remain zero in the previous day's closing report. The native successor opening has cursor 6 and settlement count 1; its close has cursor 8 and settlement count 2. No trades or new fees are expected on this holding day.

The successor request and native receipt identify the continuation manifest and executing runtime. The original files and reports remain unchanged and remain verifiable with the original runtime. A lost process resumes from the same native event cursor, and completed phases remain idempotent. Corrupt archived state, changed holdings, parent pointers, runtime, or manifests refuse before a successor worker.

The tests use a separate process running the actual frozen pre-extension source to build and close a controlled parent, then the candidate source to restore it. They cover close settlement interruptions, continuation interruptions, T+1, one native account identity, unchanged cash and first-day bytes, holding rather than refilling a cancelled remainder, plan-only CLI behavior, and altered binding rejection. These are synthetic clock/transport fixtures, not evidence of real cross-day observation.

No production account is bound by development or tests. The existing frozen v2 close command does not depend on this candidate or its review. Tomorrow's account binding and observed day remain separate from today's successful intraday simulation and from the earlier unsuccessful pre-open plan.
